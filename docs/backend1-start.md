# С чего начать Backend 1

В итоговом плане «Мадригал итог 16 октября» от 11.10.2026 Backend 1 отвечает за workspace-service и capture-service, BASE-01, BASE-06 и INT-04. Backend 2 отвечает за Analysis, Gateway, общий каркас BASE-03, HTTP-контракты и библиотеку заданий. Это распределение отличается от прежнего сокращённого недельного плана, где минимальный Workspace временно передавался Backend 2.

Рабочая ветка Backend 1 — backend/capture; в ней могут находиться изменения обоих твоих сервисов. По итоговому плану Workspace не должен параллельно реализовываться Backend 2 из-за прежнего названия его ветки.

## Первый шаг — BASE-01

Данные уже находятся в [testdata](../testdata/README.md). Сначала прочитай [README набора](../testdata/sample_protocol/README_RU.md) и [manifest](../testdata/sample_protocol/dataset_manifest.json), затем открой в Wireshark [01_configuration.pcap](../testdata/sample_protocol/research/01_configuration.pcap).

1. Найди клиент 10.77.0.10 и устройство 10.77.0.20:46123; сопоставь направления с пакетами и временем.
2. Выдели два последовательных соединения первого файла. Одинаковые адреса/порты не означают один экземпляр соединения.
3. Посмотри исходные байты выбранного кадра и Follow TCP Stream. Сопоставь несколько действий с [CSV](../testdata/sample_protocol/action_journal.csv); связь по времени остаётся предположением до проверки байтов.
4. Посмотри research/03_combined_messages.pcap: граница TCP-пакета или одной отправки клиента не является достаточным основанием для границы прикладного сообщения.
5. С Backend 2 согласуй минимальный framing по наблюдаемым данным. Дополнительный файл используй для проверки правил после их первоначальной формулировки.
6. Зафиксируй контрольные примеры: конкретный файл, номер пакета, направление, диапазон байтов, ожидаемый результат или явно неизвестное значение.

Проверка комплектности архива уже выполнена. BASE-01 ещё требует исследования байтов, выбора framing и контрольных ожиданий; сама распаковка эту задачу не закрывает.

pcapgo поддерживает офлайн-чтение PCAP/PCAPNG без установки C-библиотеки libpcap. Версию зависимости закрепляем совместно с Backend 2. Для TCP-сборщика отдельно проверяем сохранение всех источников: выдачи только склеенных байтов недостаточно для SourceMap.

Если основа Go уже знакома, на первый проход документации выдели примерно 2–3 часа, далее читай конкретные разделы по текущей задаче.

## Что согласовать с Backend 2 перед общими моделями

- Расположение модулей Go, сервисов и общего пакета типов; это часть общего каркаса.
- projectId, captureId, sessionId, streamId, assemblyId, settingsVersion и форматы ошибок.
- SourceRange: SHA-256 записи, packetNo от 1, смещение от начала захваченного кадра от 0, длина. Диапазоны [start, end).
- SourceSpan: связь диапазона конкретного streamId/assemblyId с одним или несколькими исходными диапазонами; ретрансляции сохраняют дополнительные источники.
- Внутренний GET /internal/v1/projects/{projectId}/context и чтение закреплённых assembly-views для Analysis.
- Формат cap_/ws_ заданий, отмена и поведение после рестарта; подключаем общий механизм BASE-05.
- Каждому сервису собственная SQLite и каталог файлов; прямого доступа к БД соседнего сервиса нет.
- Точное представление времени/больших смещений в JSON и ограничения диапазонного чтения.

## Базы уже подготовлены

В проект добавлены отдельные SQLite-базы Workspace/Capture, SQL-миграции, команда запуска и тесты. Начни с [описания БД](database.md): там назначение таблиц, связи, пример SourceMap и ограничения текущей реализации.

Из корня репозитория выполни `go run ./cmd/migrate -action status`, затем `go test ./...`. Схема хранения уже есть; обработчики API, сохранение файлов, reader, jobs и TCP-сборщик ещё требуют реализации. Общий Go-модуль и точки подключения согласуй с Backend 2 при интеграции общего каркаса.

## Первая небольшая задача с кодом

Сделай отдельный исследовательский reader: он открывает один PCAP/PCAPNG и для каждого пакета выдаёт packetNo, время, capture/original length, исходные байты, адреса/порты, TCP seq/ack/flags, координаты payload в кадре.

Это ранний прототип CAP-04/05 для проверки выбранной библиотеки и координат. Он не закрывает production-задачи с загрузкой, заданиями, хранением и HTTP API. Его можно разрабатывать, пока Backend 2 готовит общий каркас.

Критерии проверки:

- байты и длины нескольких пакетов совпадают с Wireshark;
- оба формата читаются, неполный пакет виден как неполный;
- payload offset вычисляется из заголовков, не фиксируется числом 54;
- неизвестные и неподдержанные данные дают диагностику;
- reader не пытается определять границы прикладных сообщений по TCP-пакетам.

## Затем реализация по зависимостям

1. WS-01 → WS-02 → WS-03: схема Workspace, POST /api/v1/projects, GET /api/v1/projects, GET /api/v1/projects/{projectId}, версии настроек и внутренний context. Созданный проект сохраняется после рестарта; повтор создания не создаёт дубль.
2. CAP-01 → CAP-02 → CAP-03: изолированное хранилище, общие jobs, потоковая загрузка, SHA-256 и список записей. Ответ загрузки — 202 с jobId.
3. CAP-04 → CAP-05: production-reader, индекс и точное чтение исходного пакета.
4. CAP-06 → CAP-07 → CAP-08: поколения соединений, восстановление TCP и SourceMap; затем версии assembly и чтение диапазонов.
5. До объявления корректности проверить пропуски, усечение, конфликты, отсутствие начала и checksum на diagnostics. Эти условия не должны превращаться в выдуманные байты или ложный PASS.
6. Журнал, гипотезы, перенос, отчёт и общая приёмка идут по итоговому бэклогу после выполнения зависимостей.

Перед сдачей первого reader есть конкретный результат для команды: один исходный пакет и его TCP-payload с проверенными координатами. На него уже можно опереться при проектировании SourceMap и API.
