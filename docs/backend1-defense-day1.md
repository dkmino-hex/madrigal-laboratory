# Защита Backend 1 — первый день

Материал к результату 12 октября 2026. Подробная инструкция запуска — `backend1-day1.md`. Это локальная заметка, исключённая из Git действующим `/docs/`.

## Как объяснить проект за минуту

«Мы делаем лабораторию исследования неизвестного бинарного протокола. Инженер загружает PCAP, сопоставляет байты с действиями клиента, формулирует правило и проверяет его на дополнительной записи. Вывод должен сохранять ссылки на точные исходные пакеты и диапазоны байтов. Моя часть — Workspace и Capture. В первый день я подготовил хранение и API проектов, неизменяемое хранение оригиналов и сохраняемые задания, а также исследовал контрольный корпус. Полный TCP-сборщик и декодер относятся к следующим этапам».

## Как объяснить сегодняшние задачи

**BASE-01 — исследование входных данных.** Сначала выясняем, какие форматы и случаи действительно нужно поддержать. Наш baseline содержит два последовательных TCP-соединения с теми же адресами и портами. Поэтому один 4-tuple не равен одному соединению. Проверили, что заголовок прикладного сообщения может быть разрезан между TCP-пакетами, а пакет может содержать несколько сообщений. Зафиксировали гипотезу framing и контрольные координаты для будущего SourceMap.

**WS-01 — схема хранения.** Workspace владеет проектами и исследовательскими метаданными, Capture — записями и байтами. У сервисов разные SQLite-файлы. Между ними передаются идентификаторы и версии; SQL JOIN через чужую БД не используется. Миграции — последовательные версии схемы, встроенные в Go binary через go:embed. Контрольная сумма защищает уже применённый SQL от незаметного изменения. Новое изменение оформляется новой миграцией, как 0005_job_stages.sql.

**WS-02 — проекты.** POST создаёт проект и начальную неизменяемую конфигурацию одной транзакцией. GET открывает проект; список возвращается страницами. Повтор POST возможен из-за сетевого сбоя: клиент не знает, успел ли сервер сохранить результат. Idempotency-Key позволяет безопасно повторить запрос. Сравнение хеша тела не позволяет тем же ключом создать совершенно другой проект.

**CAP-01 — оригиналы.** Имя файла можно изменить, содержимое — нет. SHA-256 идентифицирует конкретные байты. Потоковая запись не требует держать весь файл в оперативной памяти. Пока запись не завершилась, файл лежит в staging. После синхронизации публикуется объект по хешу, затем фиксируются метаданные. SQLite и каталог оригиналов не образуют общую транзакцию: последовательность специально выбрана так, чтобы сбой оставил лишний объект, а не опубликованную ссылку на недописанный файл. При запуске проверяется целостность оригиналов.

**CAP-02 — фоновые задания.** Долгая обработка — сохраняемая запись в jobs, а не только goroutine. Пользователь видит состояние, этап и прогресс. Capture и job создаются одной локальной SQL-транзакцией. Worker берёт одно задание, поддерживает context/cancel и сохраняет итог. После аварии RUNNING не означает успешную обработку: оно становится FAILED с PROCESS_INTERRUPTED. Незавершённая assembly остаётся недоступной как готовая.

## Вопросы, которые вероятны на защите

**Почему SQLite?** Для текущего локального исследовательского приложения проще запуск и меньше инфраструктуры: БД встроена в процесс и хранится в файле. У каждого сервиса свой файл и свои миграции. Микросервисная граница определяется владением данными и API, а не наличием отдельного сервера СУБД. Ограничение — один писатель на файл и один активный worker Capture; горизонтальное масштабирование на общий файл не предусмотрено.

**Зачем миграции, если можно один раз создать таблицы?** Схема меняется вместе с приложением. Миграции позволяют воспроизвести актуальную схему на другой машине и последовательно обновить существующую БД. Редактировать применённую миграцию нельзя: checksum обнаружит расхождение.

**Что гарантирует транзакция?** Проект, настройки и ответ для повтора либо сохраняются вместе, либо не сохраняются. Аналогично capture и job. Это гарантия внутри одного SQLite-файла; она не охватывает соседний сервис и каталог оригиналов.

**Как два одновременных POST не создадут дубль?** Создание начинается с BEGIN IMMEDIATE: SQLite сериализует писателей одного файла. Первый сохраняет проект и ответ; второй после ожидания начинает свою транзакцию и видит сохранённый ответ. PRIMARY KEY в idempotency_keys дополнительно задаёт уникальность ключа в scope. Если тела различаются — 409. Ожидание ограничено busy_timeout=5000.

**Как исключён второй worker?** Перед восстановлением заданий worker берёт системную файловую блокировку рядом с БД. Второй процесс получает отказ. ОС освобождает блокировку после завершения процесса; удалять lock-файл для запуска не требуется.

**Что такое WAL?** Изменения сначала попадают в журнал рядом с БД, затем checkpoint переносит их в основной файл. Режим помогает совместить чтение с записью, но не разрешает нескольких одновременных писателей. Для резервной копии живой БД нужен SQLite backup API или согласованная остановка с checkpoint, а не копирование одного .sqlite.

**Зачем хранить hash запроса?** Один ключ должен означать одну операцию. Иначе повтор с другим именем мог бы получить ответ от прежнего проекта и скрыть ошибку клиента.

**Почему cursor, а не OFFSET?** Продолжаем после конкретной пары created_at/id в устойчивом порядке. Не нужно каждый раз пропускать все предыдущие строки. Это не обещание одного общего снимка списка при параллельных вставках.

**Почему сначала файл, потом БД?** При обратном порядке можно опубликовать метаданные ещё недописанного файла. В нашем порядке сбой между публикацией файла и Commit оставляет лишний объект, который безопасно узнаётся по хешу. При старте проверяется существование и SHA-256 всех ссылочных оригиналов.

**SHA-256 — это шифрование?** Нет. Хеш — отпечаток содержимого. Он нужен для идентичности, обнаружения повтора и проверки целостности; он не делает содержимое секретным и сам по себе не удостоверяет автора.

**Что случится при рестарте worker?** QUEUED сохраняется. Прежние RUNNING завершаются явной ошибкой PROCESS_INTERRUPTED; связанные незавершённые ресурсы получают ошибку. Существующий успешный результат не создаётся заново и не дорисовывается.

**Чем отмена отличается от ошибки?** Отмена — намерение пользователя остановить операцию. Для RUNNING сначала сохраняется cancel_requested, затем handler прекращает работу через context и worker фиксирует CANCELLED. Ошибка выполнения фиксируется FAILED с причиной. Терминальные состояния повторным cancel не меняются.

**Почему одного cap_ префикса недостаточно?** Префикс помогает Gateway выбрать сервис-владелец. Наличие задания всё равно проверяется в БД. Авторизация доступа к чужим исследованиям — отдельная задача, текущий стенд локальный.

**Почему TCP-пакет не является сообщением протокола?** TCP передаёт упорядоченные байты. Одно прикладное сообщение может оказаться в нескольких сегментах, несколько сообщений — в одном. В нашем combined_messages это проверяется конкретными пакетами 4/6/8 и 10.

**Какой framing найден?** Кандидат: A6 5C, 8-байтовый заголовок, длина тела uint16 big-endian на смещении 2; полная длина 8+length. Правило проверено на предоставленном корпусе, но не доказывает устройство любого неизвестного протокола.

**Что такое big-endian?** В паре 00 0A старший байт идёт первым: значение 10. Для length=10 полное сообщение занимает 18 байт.

**Что означает [start,end)?** Начало включено, конец исключён. Длина равна end-start. Поле [2,4) занимает два байта со смещениями 2 и 3. packetNo начинается с 1, frameOffset — с 0 от начала захваченного кадра.

**Как связать поле с оригиналом?** Поле хранит диапазон потока конкретной assembly. SourceMap сопоставляет его с captureSHA256, packetNo и диапазоном кадра. Для поля длины первого запроса baseline нужны пакет 4 [56,57) и пакет 6 [54,55). Полный SourceMap реализуется следующими задачами; сегодня закреплены входные контрольные примеры и схема хранения.

**Можно ли заполнить пропуск нулями?** Нет: ноль — конкретное значение, отсутствие байтов — неизвестность. Иначе можно получить ложный вывод. Пропуск, конфликт и неизвестное начало требуют явной диагностики и INCONCLUSIVE.

**Почему неверная checksum не всегда повреждение?** При локальном захвате аппаратное вычисление checksum может завершиться уже после точки наблюдения. По одному несовпадению нельзя уверенно различить offload и повреждение. Наш probe сообщает INVALID_OR_OFFLOAD, решение требует контекста захвата/настроек. Упоминание offload в README набора не превращает эвристику в доказательство для любых записей.

## Показ за 5–7 минут

1. Показать два запущенных Go-сервиса и их readyz; при Docker-запуске — один healthy контейнер с двумя процессами и двумя отдельными SQLite-файлами.
2. POST проекта, затем повтор с тем же ключом: projectId одинаковый. Изменить имя при прежнем ключе: 409.
3. Открыть GET карточки и список с limit=2. Объяснить settingsVersion и nextCursor.
4. Подготовить baseline через `docker compose exec -T laboratory capture-prepare` внутри контейнера. Показать SHA-256 и QUEUED cap_ job. Повторить и показать duplicate:true.
5. Отменить QUEUED, показать CANCELLED. Объяснить, что worker индексации будет подключён в следующих задачах.
6. Перезапустить workspace-service и capture-service, повторно открыть проект и задание: данные сохранились.
7. Показать acceptance JSON: SYN 1/96 baseline; сообщение на нескольких пакетах; length [2,4) → два исходных диапазона.
8. Запустить `go test -count=1 ./...` без внешней БД. Рассказать, какие реальные гонки и сбои проверяются во временных SQLite-файлах.
