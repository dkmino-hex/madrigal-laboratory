# Как работать с Мадригалом

Руководство для текущей объединённой версии, 15 октября 2026 года. Начальная страница: <http://127.0.0.1:8080/projects>. Для первого знакомства достаточно браузера и учебных файлов из `testdata/sample_protocol`. Программа работает с незашифрованным TCP/IPv4 поверх Ethernet.

## 1. Что ты здесь исследуешь

PCAP содержит то, что устройства передали по сети. Сам по себе файл не говорит, где находится температура и что означает команда. Журнал сообщает, какое действие выполнял человек и какой результат показал штатный клиент. Лаборатория сопоставляет эти два источника, предлагает объяснение байтов и позволяет проверить его на другом эксперименте.

Пример: при настройке порога на −2,5 °C два байта читаются как −250; при настройке на 21 °C — как 2100. Возможное объяснение: это знаковое двухбайтовое число, которое нужно разделить на 100. Смысл «температурный порог» приходит из контекста опыта; совпадение чисел требует проверки на новых значениях.

Тебе не нужно начинать с придумывания имён полей. Сначала загрузи записи и журнал, затем открой **«Сравнение примеров»**. Там программа предложит участки, типы и формулировки наблюдений.

## 2. Запуск и сохранность данных

Из корня проекта:

```powershell
docker compose up --build -d --wait
docker compose ps
```

После запуска открой адрес выше. Все четыре службы должны иметь состояние `healthy`. Первая сборка требует сети для зависимостей; уже подготовленные образы работают локально. Повторный запуск подготовленных образов без пересборки: `docker compose up -d --wait`.

Данные хранятся в Docker-томах `madrigal-integration_workspace-files`, `madrigal-integration_capture-files`, `madrigal-integration_analysis-data`. Обычное закрытие браузера и перезапуск контейнеров их сохраняют. `docker compose down -v` удаляет тома и данные — эта команда не нужна для обычной работы.

Бэкап перед добавлением автоматики: `D:\Проекты\madrigal-backup-20261015-033721`. В нём есть исходники с незакоммиченными изменениями, старые образы, согласованные архивы трёх томов, SHA-256 и отдельная инструкция восстановления. Данные, добавленные после создания этого бэкапа, в него не входят. Для передачи нового исследования используй экспорт проекта ZIP.

## 3. Первый опыт за один проход

1. Создай проект, например «Исследование термостенда».
2. В обзоре загрузи `research/01_configuration.pcap`, `research/02_variations.pcapng`, `research/03_combined_messages.pcap`. Дождись завершения заданий, а не только окончания передачи файла.
3. Открой «Журнал действий», импортируй `action_journal.csv` с UTC и поправкой времени 0. Этот CSV содержит также строки для дополнительного и диагностического корпусов; без соответствующих записей они не создают сетевых примеров.
4. Открой «Сравнение примеров». Анализ запустится автоматически для выбранных готовых записей. В списке «Записи для подбора» оставь только первые три.
5. В «Что ищем в сообщениях» выбери «Температурный порог, °C». Найди вариант «Целое со знаком, 2 байта, старший байт первым, разделить на 100». В проверочном прогоне по трём учебным записям он совпал в 9 из 9 однозначных примеров группы B→A, смещение 12, длина 2. Его технический путь — `params.threshold_c`, тип — `int16be`; они видны в подробностях. Это пример результата, не обещание одинакового порядка карточек и IDs.
6. Нажми «Сохранить наблюдение». В форме будут название, пример «байты → значение», расчёт и готовый текст. Проверь его и сохрани. Нажми «Создать схему для проверки» в сообщении об успехе или на основном экране.
7. Перейди в спецификацию по появившейся ссылке. Она открывается с полным примером сообщения для предварительного разбора.
8. Загрузи `additional/04_new_observations.pcapng`. Она содержит другие значения; не включай её задним числом в подбор, если хочешь проверить исходную гипотезу независимо.
9. В «Проверках корпуса» выбери созданную интерпретацию и её ревизию, добавь сборку дополнительной записи в корпус и запусти проверку.
10. Посмотри PASS, FAIL, INCONCLUSIVE и NOT_APPLICABLE. Перейди из результата к конкретным байтам. Сформируй отчёт и экспортируй проект ZIP.

На дополнительной учебной записи созданное правило сравнения порога с журналом дало 3 PASS и 0 FAIL. Остальные сообщения могут быть неприменимы к этой частичной схеме. Это не означает, что весь протокол описан.

Учебные прикладные байты получены обменом клиента и симулятора по TCP; пакетные заголовки и временная шкала смоделированы. Происхождение набора подробно описано в `testdata/README.md` и оригинальном `README_RU.md`.

## 5. Запись, сессия, направление и сборка

**Запись** — один исходный PCAP/PCAPNG. SHA-256 идентифицирует его содержимое. Повторная загрузка тех же байтов не должна создавать второй независимый эксперимент.

**Сессия** — конкретный экземпляр TCP-соединения. Одинаковые адреса и порты при переподключении могут относиться к другой сессии.

**A→B / B→A** — стороны соединения. По этим обозначениям нельзя автоматически заключать, кто клиент и кто сервер, особенно если начало соединения отсутствует.

**Сборка** — восстановленный поток при определённой версии настроек. Изменение checksum или другой политики требует новой сборки. Старые ссылки остаются привязаны к старой сборке; они не переезжают на другие байты.

**Фрейминг** — правило выделения сообщений внутри потока. Одно сообщение может занимать несколько TCP-пакетов, а один пакет — содержать несколько сообщений. Надпись «TCP-фрагмент» означает, что прикладная граница ещё не установлена.

## 6. Журнал: откуда берутся названия и значения

Поддерживаются исходные восемь колонок учебного CSV:

```text
capture,session,action_id,start_utc,end_utc,action,parameters,observed_result
```

`parameters` и `observed_result` содержат JSON внутри CSV-ячейки; кавычки должны быть экранированы по правилам CSV. Сохраняй файл в UTF-8. Есть также компактный формат `timestamp,name,type,parameters`; он не содержит полного окна и привязки к записи.

Автопоиск извлекает числовые параметры в виде путей: `params.threshold_c`, `params.period_ms`, `observed.measurements[0].temperature_c`. Вложенные объекты и первые элементы массивов поддерживаются в пределах интерактивных лимитов. Строковое имя устройства само по себе не становится числовым кандидатом.

Пример связывается с журналом **по имени файла записи и времени исходного пакета**, до сравнения чисел. Имя `session` в CSV сохраняется как метка опыта; оно не объявляется установленным TCP sessionId. Отсутствие поля capture в компактном CSV означает поиск по времени среди выбранных записей. Используй уникальные базовые имена файлов для разных опытов: совпавшие имена и окна могут дать неоднозначность.

Если окна нескольких действий совпали, программа не выбирает действие только потому, что его число подходит. Противоречивые значения остаются неизвестными. Неправильные часы или имя файла дают отсутствие связи; это не доказательство отсутствия поля.

Для синхронизации выбирай часовой пояс и поправку в наносекундах при импорте. Поправка применяется один раз. Временная метка относится к наблюдению пакета в точке захвата, а не к внутренним часам устройства.

После импорта смотри принятые/отклонённые строки и диагностику задания. Не считай успешную загрузку файла успешным разбором всех строк.

Чтобы сохранить ручную связь, нажми «Выбрать действие», укажи запись, сессию, направление и диапазон, затем «Сохранить ручную связь». Начало и длина отсчитываются в байтах восстановленного потока: начало 0 и длина 4 означают первые четыре байта, а не автоматически найденное поле температуры. Найти нужный участок помогает «Посмотреть выбранные байты и пакеты» или автоматическое сравнение.

Перед сохранением программа сама получает ссылки на исходные пакеты выбранного диапазона и SHA-256 записи. Вводить их вручную не нужно. Если в диапазоне нет сохранённых исходных байтов, выбери другой участок по просмотру обмена. Основание поясняет связь с действием; текст «Изменение температуры» сам по себе не устанавливает назначение выбранных байтов. У уже сохранённой связи можно уточнять основание и уверенность, сохраняя прежние источники.

## 7. Как читать автоматическое сравнение

«Записи для подбора» определяет исходную выборку. Можно выбрать до восьми готовых записей и направление. После изменения выбора нажми «Найти примеры и кандидаты»; старый результат сбрасывается.

Программа пытается найти повторяемую границу по заголовку и длине. Это эвристика, её основания и ограничения находятся в раскрывающемся блоке. Если достаточного основания нет, сравниваются известные TCP-фрагменты с явной отметкой. Не принимай любую строку матрицы за гарантированно правильное сообщение.

Группы разделяют направления и предполагаемые семейства сообщений. Условие вроде `@7=20` означает группировку по байту в позиции 7, а не установленное название команды. Кандидаты относятся только к выбранной группе.

На основном экране:

- «Что ищем в сообщениях» показывает понятное название известного значения, например «Время устройства, мс · измерение №1». Это отображение имени из журнала; технический путь доступен в подробностях;
- верхняя карточка показывает найденный способ чтения и число совпадений;
- слева в «Примерах» по умолчанию открыт вид «Байты»: действие и файл, значение журнала, прочитанное число и HEX-столбцы. Выбранное поле подсвечено; таблица автоматически прокручивается к нему. Первые три столбца остаются на месте при горизонтальной прокрутке;
- кнопка «Значения» показывает подробную таблицу с временем, байтами поля и результатом сопоставления. Оба вида используют одинаковые фильтры и выбранный пример;
- нажми на пример или используй стрелки ↑ ↓: панель «Выбранный пример» покажет его данные. На узком экране панели располагаются друг под другом; у разбора есть кнопки предыдущего/следующего примера;
- в разборе видны HEX, число с единицей, расчёт масштаба и расположение поля. Нажатие на поле раскрывает байты сообщения с подсветкой;
- «Только отличающиеся» оставляет контрпримеры. Поиск принимает имя файла, действие или значение; число показанных примеров видно отдельно;
- «Открыть исходные пакеты» ведёт к физическим источникам. «Вернуться к сравнению» сохраняет группу, поле, выбранный пример и записи;
- справа всегда видны «Кандидаты в поля»: позиция, тип чтения, масштаб, число совпадений и контрпримеры. Нажатие на вариант меняет подсветку и разбор. Нажатие на контрпример сразу выбирает соответствующий опыт и включает фильтр отличий.

Полная матрица доступна в раскрывающемся разделе «Полная матрица байтов · для подробного анализа». В ней:

- слева — пример и переход к физическому источнику;
- «Журнал» — известное значение выбранного параметра;
- «Прочитано» — значение по выбранному кандидату;
- остальные столбцы — HEX-байты; номера позиций показаны десятичными числами, HEX-код позиции находится в подсказке;
- интенсивность цвета показывает изменчивость, штриховка — наличие позиции не во всех примерах;
- синяя граница выделяет выбранный кандидат, красное значение — контрпример.

Матрица прокручивается горизонтально; кнопка «Показать столбцы выбранного поля» переводит к нужному участку. Она показывает текущую страницу списка, до 24 примеров, с теми же фильтрами. Позиции в разборе, матрице и JSON-схеме указаны десятичными числами и отсчитываются от начала сообщения с нуля. Положение в восстановленном потоке может быть другим.

`int16be ÷ 100` означает: взять два байта, старший первым, прочитать знаковое число, разделить на 100. Например, `FF 06` = −250 → −2,5. `uint16be` прочитал бы те же байты как 65286 → 652,86; отрицательные опыты помогают отвергнуть такой вариант.

Счётчик `9/9` относится к однозначным числовым примерам этой группы. Строки без однозначного ожидаемого значения перечисляются отдельно и не превращаются в совпадения. Минимум для предложения: два разных совпавших значения, минимум два совпадения, не менее половины подходящих примеров. Несколько типов или смещений могут проходить этот порог одновременно.

Кандидаты «постоянный участок» и «изменяющийся участок» описывают факт о выборке. Они не объясняют смысл поля. Семантические имена из воздуха программа не придумывает.

## 8. Наблюдение и гипотеза

Из кандидата текст, основание и примеры заполняются автоматически. Сначала видны понятное имя и реальный пример с байтами, числом и расчётом. Можно исправить текст «Что удалось заметить». Вид записи и основания доступны в «Тип записи и технические основания», полный список файлов, действий и пакетов — в «Источники, которые сохранятся вместе с записью». Кнопка сохранения остаётся в нижней части формы при прокрутке. Доступны типы:

| Тип        | Пример                                                           | Что подтверждает                                  |
| ---------- | ---------------------------------------------------------------- | ------------------------------------------------- |
| Наблюдение | «Байты 12–13, int16be ÷100, совпадают с журналом в 9/9 примеров» | Факт сопоставления в указанной выборке            |
| Гипотеза   | «Это поле передаёт установленный температурный порог»            | Предполагаемое назначение, требующее новых опытов |

Сохранение атомарно: запись и все источники сохраняются вместе. При ошибке одного источника не остаются отдельные бесхозные связи. Повтор одного запроса с тем же ключом не создаёт дубль. Новый осознанный клик после перезагрузки может создать новую запись.

Сохраняются версия алгоритма, отпечаток входов, ID кандидата и статистика. Прикладывается до 12 поддерживающих и 12 противоречащих источников. Полный счётчик и число приложенных примеров могут отличаться — это явно показано в основании.

Автоматическая запись получает открытый статус, источники — tentative. Назначение поля не получает автоматический статус «подтверждено». При изменении текста происхождение автоматического предложения сохраняется.

Без журнала можно открыть «Обмен и байты», выделить 1–256 известных байтов и нажать «Создать наблюдение из выделения». Получится текст с координатами и HEX, с привязкой к исходным пакетам. Неизвестные и конфликтующие байты такой текст не подменяет догадкой.

## 9. Подсветка в HEX и происхождение

В «Обмене и байтах» справа есть два режима: «Сообщения и поля» и «Исходные пакеты». На мобильном экране сначала открой панель «Сообщения / пакеты».

В режиме «Сообщения и поля» выбери «Разбирать по схеме» и сохранённую ревизию. Список показывает сообщения **текущего окна HEX и текущего направления**, а не весь корпус. Нажми на сообщение, затем на поле: в HEX и ASCII выделятся его байты. Обратное выделение байтов выбирает соответствующее поле. В таблице указаны имя, тип, значение, позиция от начала сообщения и длина. Подпись под таблицей отдельно показывает позицию в потоке. Цвет связывает поле с байтами; пропуски и конфликты не закрашиваются как известные данные.

Поиск внутри панели фильтрует сообщения по названию, полям, значениям и позиции. Клавиши ↑ ↓ переключают сообщения. Схема, ревизия, режим панели и выбранный диапазон сохраняются в URL; смена направления сохраняет выбор схемы. Текстовое `description` в определении поля JSON-схемы отображается как пояснение. Названия известных параметров берутся из привязки правила к журналу; неизвестным полям программа не придумывает смысл.

Если схемы ещё нет, выбери «Автопоиск · кандидаты без схемы». Подбор использует выбранную закреплённую сборку и до семи других готовых записей из загруженного списка проекта. В панели остаются сообщения выбранного потока. Названия из журнала и числовые чтения помечаются гипотезами; в группе без достаточных опытов поля не выдумываются. Число использованных записей и ограничения видны рядом. Ссылка «Сравнить это поле на других примерах» открывает сравнение по нужному параметру.

Это интерактивный предварительный разбор в пределах окна (до 4096 байт). На границе окна сообщение может оказаться неполным; диагностика остаётся видимой. Preview использует текущий журнал. Для воспроизводимого результата по всему корпусу запусти «Проверку»: она закрепит ревизию, сборки, настройки и снимок журнала.

В «Обмене и байтах» нажми «Подсветить кандидаты в поля». Поиск закрепляется за выбранной записью, сборкой и направлением. Подсвечиваются только известные байты подходящих примеров текущего потока. В подсказке есть параметр и статистика; кнопки над просмотром выделяют найденный диапазон.

Подсветка — указатель для исследования. Приоритет обычного выделения сохраняется. Отсутствие подсветки может означать другую группу/сборку, ограниченную выборку, отсутствие журнала или недостаток известных байтов.

«Происхождение» показывает пакет, смещение внутри кадра, длину и соответствующее смещение потока. Одинаковые ретрансляции не дублируют прикладные байты, но остаются исходными пакетами. Конфликтующие альтернативы видны отдельно. Не смешивай смещение кадра, потока и поля сообщения.

## 10. Спецификация и ревизии

«Создать схему для проверки» сохраняет частичную интерпретацию: фрейминг, область направления/типа, поле, масштаб и правило сравнения с журналом. Остальные поля протокола ещё не описаны.

В редакторе можно менять имя поля, тип, смещение и JSON-правила. Сохранение создаёт новую ревизию; старый запуск продолжает использовать старую. Предварительный разбор работает по выбранному диапазону: он должен включать начало сообщения и достаточную длину. Диапазон из двух байтов поля недостаточен для разбора восьмибайтового заголовка.

Справа доступны формы, слева — тот же JSON. В «Границах сообщений» выбери фиксированный размер или длину из заголовка. Для второго режима задай размер заголовка, позицию длины от 0 и порядок байтов; отметь, включает ли число длины сам заголовок. Маркер HEX помогает находить начало. Переключение режима заменяет параметры длины этого режима, поэтому проверь новые значения перед сохранением.

«Добавить поле» создаёт поле uint8 сразу после предыдущего. Выбери тип, при необходимости задай позицию и масштаб. Пустая позиция означает последовательное чтение; пустой масштаб — без пересчёта. Для строк и байтов задай длину либо выбери ранее прочитанное поле длины. `description` задаётся через «Пояснение поля» и показывается в просмотре сообщений. При переименовании обновляются ссылки правил и `lengthFrom`. Используемое поле нельзя удалить, пока не убраны ссылки на него.

«Добавить правило» предлагает четыре реальных условия движка: равно, диапазон, длина, параметр журнала. Выбери существующее поле; для диапазона можно оставить одну границу пустой, для журнала укажи путь параметра и допустимое отклонение. Числовые литералы, включая uint64, сохраняются точно. Незаконченный ввод вроде `0.` блокирует сохранение; исправь значение. JSON остаётся доступным для расширений и сложных значений. Сохранение и preview используют новую неизменяемую ревизию, сервер дополнительно проверяет схему.

В автосравнении выбор «Границы сообщений для автосравнения» позволяет использовать сохранённую ревизию вместо эвристики. Выбор запоминается в ссылке. Подбор поддерживает фиксированный размер либо длину из заголовка без `lengthIncludesHeader=true`; неподходящая ревизия возвращает явную ошибку. Ревизия задаёт границы, смысл числовых кандидатов всё ещё сопоставляется с журналом.

Поддержаны фиксированная длина и длина из заголовка, знаковые/беззнаковые числа, float32, строки и байты, переменная длина через ранее прочитанное поле. Подробный формат и реальные ограничения: [схема Analysis](analysis-schema.md).

Проверка `action` сравнивает значение поля с конкретным параметром журнала. Без доступного однозначного действия она возвращает INCONCLUSIVE. Пустой список правил может дать успешный структурный разбор; он ничего не проверяет о смысле значения.

Нет универсальной поддержки TLV, циклов по массивам, вложенных произвольных структур, CRC и полного автомата состояний. Автоматически предлагается ограниченный набор простых числовых закономерностей.

## 11. Проверка корпуса и доказательность

Выбери интерпретацию, ревизию и настройки. В выборе сборки укажи запись, добавь её в корпус. Для нескольких записей повтори добавление. Все сборки должны быть готовы и использовать одну версию настроек. Корпус включает **всю добавленную сборку**, а не только выделенный RangePicker диапазон или одно направление.

Во время запуска доступны стадия, прогресс и отмена. Успешно завершённое задание означает, что вычисление закончено; внутри результата могут быть FAIL и неизвестные участки.

В завершённом запуске «Показать результаты» переключает сообщения и каждое правило отдельно. В режиме сообщений поиск идёт по полям и значениям; в режиме правил — по имени правила и объяснению. Фильтр «Правило» использует точный ID, «Исходная запись» ограничивает корпус, «Поток» — конкретный streamId. У строки правила есть кнопка «Только этот поток» и ссылка на байты. Правило без источника отображается без выдуманной ссылки. Статус отдельного правила независим от общего статуса сообщения: в сообщении с FAIL могут быть и успешные проверки.

«Скачать результаты NDJSON» выгружает все страницы с текущими фильтрами и выбранным режимом, а не только видимую страницу. Каждая строка — модель интерфейса: значения полей представлены точными строками, источники и координаты сохраняются. Это отличается от исходного DTO CLI. Файл создаётся после успешного чтения всех страниц. Для больших корпусов предпочтительнее CLI, который пишет результат по мере чтения.

В «Обмене и байтах» раскрой «История сборок записи»: видны даты, движок, закреплённые настройки, статус и диагностика каждой версии. «Открыть эту сборку» открывает первую сессию выбранной версии в текущем направлении; дальше сессии выбираются слева. Старые результаты и источники продолжают ссылаться на исходную версию.

| Статус         | Значение                                                      | Действие                                            |
| -------------- | ------------------------------------------------------------- | --------------------------------------------------- |
| PASS           | Выполнилось заданное правило либо успешно прочитана структура | Уточни, какое именно правило проверялось            |
| FAIL           | Есть противоречие правилу                                     | Открой пример, сравни байты и ожидаемое значение    |
| INCONCLUSIVE   | Недостаточно известных данных/однозначного журнала            | Проверь захват, окно времени, границы и покрытие    |
| NOT_APPLICABLE | Сообщение вне заданной области направления/типа/длины         | Проверь, ожидаемо ли это для выбранной схемы        |
| UNKNOWN        | Неизвестный/неохваченный участок                              | Исследуй отдельно, не прибавляй к успешным примерам |

`knownBytes`/`unknownBytes` описывают доступность и диагностику данных в обработанном корпусе. Это не процент доказанного назначения всех байтов протокола. Поля, которые схема не описывает, не получают смысл автоматически.

Для честной независимой проверки отложи отдельную запись **до подбора**, меняй несколько значений, включай отрицательные, нулевые, граничные случаи и другую длину ответа. Если ты подобрал схему по всем четырём записям, проверка на этих же четырёх показывает согласованность, но не новое обобщение.

Проверочный опыт: создай новую ревизию со смещением поля на один байт больше, запусти на дополнительной записи, найди FAIL. Верни правильное смещение новой ревизией и сравни запуски. В приёмочном сценарии неправильная схема дала 3 FAIL, исправленная — 3 PASS. Это проверка реальной реакции на ошибочное правило.

Запуск закрепляет SHA-256 записей, сборки, настройки, движок и, для `action`, снимок журнала. Редактирование текущего журнала не переписывает завершённую проверку. После смены ревизии или настроек старый запуск обозначается историческим. Сравнение запусков учитывает версии и состав корпуса — одинаковые проценты на разных корпусах не равнозначны.

## 12. Дефекты захвата и настройки

| Ситуация            | Как интерпретировать                                                         |
| ------------------- | ---------------------------------------------------------------------------- |
| GAP / пропуск       | Байты отсутствуют в записи; журнал не восстанавливает их                     |
| Усечение / snaplen  | Исходный кадр записан не полностью                                           |
| Конфликт перекрытия | Для одних TCP-координат записаны разные байты; исследуй альтернативы         |
| Неизвестное начало  | Нельзя гарантировать старт сообщения и роли сторон                           |
| Checksum warn       | Предупреждение сохраняется, данные доступны для анализа                      |
| Checksum strict     | Плохие сегменты исключаются; валидная ретрансляция может восполнить диапазон |
| Checksum ignore     | Проверка checksum пропускается согласно сохранённой политике                 |

При локальном захвате checksum offloading может давать предупреждения без фактической порчи обмена. Выбор политики должен быть осмысленным и сохраняться вместе со сборкой.

Движок не пытается незаметно найти «удобный» новый заголовок после несовпадения magic: остаток становится диагностикой фрейминга. Укороти предварительный диапазон до правильной границы или уточни схему. Неподдерживаемые транспорт/канальный уровень и IP-фрагментация не являются установленными прикладными сообщениями.

## 13. Отчёт, ZIP и передача проекта

На странице завершённого запуска нажми «Сформировать Markdown-отчёт», дождись задания и скачай файл в «Отчётах и переносе». В отчёт входят закреплённый run, сводка, результаты, наблюдения, основания, физические источники, происхождение автоматических предложений, журнал и открытые гипотезы. Технические результаты включают JSON; это позволяет сверить точные значения.

Отчёт сохраняет снимок Workspace на момент запроса. Если после этого изменил наблюдение, создай новый отчёт. Ранее скачанный файл не обновляется. Для больших результатов есть явный защитный предел, превышение приводит к ошибке задания, а не к «полному» обрезанному отчёту.

Экспорт ZIP переносит исходники, настройки, схемы, наблюдения, связи и результаты. Импорт создаёт отдельный проект с новыми IDs и переводит ссылки на восстановленные объекты. Старые абсолютные пути не нужны. Снимки происхождения остаются историческими; идентификатор исходного действия внутри закреплённого снимка run не следует считать ссылкой на текущий UI после переноса.

Кнопки переноса находятся сверху **на каждой странице проекта**, в строке «Архив проекта»:

1. Нажми «Экспортировать проект ZIP». Подготовка начнётся сразу, в открывшемся окне будет показан её ход.
2. После завершения нажми «Скачать ZIP». Архив останется также в «Отчётах и переносе». Закрытие окна не отменяет подготовку; пока она продолжается, повторное нажатие на экспорт открывает то же задание.
3. Для восстановления нажми «Импортировать ZIP» — эта кнопка есть и в списке проектов. Выбери скачанный файл и нажми «Импортировать проект ZIP».
4. Дождись окончания проверки архива и нажми «Открыть импортированный проект». Будет открыта отдельная восстановленная копия, исходный проект сохранится.

Экспорт доступен для готового проекта. Повреждённый архив не открывается как готовое исследование; причина видна в задании импорта.

ZIP не заменяет установленное приложение: получателю нужны совместимые образы/исходники и Docker. Перед переносом дождись завершения заданий. Не редактируй содержимое ZIP вручную: целостность проверяется.

## 14. Повторное применение без ручного описания примеров

Нужны Node.js 22.12+ на машине запуска, работающий Gateway, ID проекта, сохранённой ревизии и уже загруженной новой записи. Из корня репозитория:

```powershell
node scripts/apply-interpretation.mjs --project YOUR_PROJECT_ID --revision YOUR_REVISION_ID --capture YOUR_NEW_CAPTURE_ID
```

Подставь реальные IDs из адресной строки/API. Несколько записей: повтори `--capture ID`. Другой сервер: `--gateway http://127.0.0.1:8080`. Каталог результата: `--out output/my-check`; он должен быть новым. При повторном запуске используй новый каталог.

На странице «Отчёт» выбери завершённый запуск и нажми «Копировать команду PowerShell». Команда включает его ревизию и `--assembly ID` для каждой записи, сохраняя выбранные версии потоков. При ручном вводе `--assembly` нужен один аргумент на каждый `--capture` в том же порядке; без него используется последняя готовая сборка. Новый запуск закрепляет текущий журнал: для изучения прежнего снимка используй исходный запуск или его отчёт.

Команда выбирает готовую сборку каждой записи, проверяет совместимость настроек, создаёт run, ждёт задание и выгружает весь список сообщений страницами. Результат: `run.json` с условиями и сводкой, `results.ndjson` — одно сообщение на строку с полями, правилами и источниками. Код завершения 0 означает успешное выполнение команды; наличие FAIL нужно смотреть в сводке. Ошибка/таймаут оставляет явное сообщение, частичный файл не объявляется полным. Таймаут клиента сам по себе не отменяет серверное задание.

Для `action` в проекте должен быть журнал новой записи. Для структурных `eq/range/length` журнал не обязателен. Утилита ничего не подставляет по именам учебных файлов и не переописывает каждое сообщение.

## 15. Защитные пределы и частые вопросы

Интерактивный автопоиск отличается от полного запуска Analysis:

| Ограничение автопоиска        | Текущее значение                                               |
| ----------------------------- | -------------------------------------------------------------- |
| Записи                        | До 8 выбранных READY                                           |
| Байты проекции                | 256 КиБ на запись, до 128 КиБ одного потока                    |
| Потоки / физические источники | До 64 потоков и 4096 источников на запись                      |
| Матрица                       | До 128 примеров, первые 128 байтов примера                     |
| Сообщение автоподбора         | До 4096 байтов                                                 |
| Кандидаты                     | До 12 на группу, до 80 суммарно                                |
| Журнал подбора / action       | До 2000 действий и 2 МиБ их данных                             |
| Глубина/массивы/числовые пути | До 5 уровней, первые 8 элементов массива, до 48 путей действия |

При достижении лимита результат помечается ограниченным, основания находятся в предупреждениях. Даже `complete=true` не означает, что описан весь протокол: матрица показывает оговорённую ширину, а алгоритм проверяет ограниченные классы гипотез. Более длинный ответ можно исследовать вручную и разобрать полной схемой; для Analysis блок/сообщение ограничены 1 МиБ, корпус — 100 сборками, выполнение — 10 минутами. Защитный предел Capture — 250000 пакетов на импорт. Это ограничения реализации, не свойства протокола.

**«Ничего не найдено».** Проверь READY, выбранные записи/направление, имена файлов и время журнала. Нужны разные значения; один повторяющийся параметр не позволяет определить поле.

**«Всё зелёное, значит температура доказана?»** Посмотри checks. Успешное чтение числа и совпадение с журналом — основания для гипотезы. Нужны новые контролируемые опыты и исключение альтернатив.

**«После изменения настроек ничего не меняется».** Старая сборка намеренно сохранена. Создай новую сборку при нужных настройках и новый run.

**«Ошибка предварительного разбора».** Выдели целое сообщение от заголовка. Если magic/длина неверны, сначала исправь фрейминг.

**«Сравнение не реагирует на новые записи».** Обнови выбор записей и нажми запуск поиска. Завершённый результат является снимком входов.

**«Откуда берётся нагрузка?»** Импорт, восстановление TCP, анализ, отчёт и ZIP выполняются заданиями; просмотр имеет пагинацию и ограниченные окна. Полный профиль PDF 100 МиБ / 1000 сессий / 100000 сообщений и пиковая память на Linux 4 vCPU/8 ГиБ пока не подтверждены измерением. Подробная честная сверка: [аудит требований](requirements-audit.md).

**«Нужен интернет?»** Для подготовки зависимостей/образов — да. Для исследования в уже запущенном приложении — нет. Автоматика локальная и детерминированная, внешняя модель ИИ не вызывается.
