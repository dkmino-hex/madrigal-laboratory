## Ручки первого дня

Базовый префикс `/api/v1`.

| Метод и путь | Запрос | Результат |
|---|---|---|
| POST /projects | JSON name и необязательные settings; обязательный заголовок Idempotency-Key | 201, projectId/name/status/settingsVersion/createdAt/updatedAt |
| GET /projects | limit 1…100, по умолчанию 50; необязательный cursor | 200, items и nextCursor при наличии следующей страницы |
| GET /projects/{projectId} | ID проекта | 200, карточка; 404 при отсутствии |
| GET /jobs/{jobId} | cap_ ID; порт Capture 8082 | Состояние, этап, прогресс, ошибка, временные метки и resourceId |
| POST /jobs/{jobId}/cancel | cap_ ID | Текущее состояние; QUEUED отменяется сразу, RUNNING получает запрос отмены |
| GET /healthz | Без тела | Процесс принимает запросы |
| GET /readyz | Без тела | Подключение к собственной БД доступно |

Каждый ответ имеет X-Request-ID. Ошибка — JSON с code/message/requestId. Большие счётчики задания передаются строками. Время — RFC3339 с UTC. Состояния проектов READY/IMPORTING/ERROR остаются различимыми.

## Демонстрация проектов

```powershell
$headers = @{ 'Idempotency-Key' = 'defense-day1-project' }
$body = @{ name = 'Thermostand'; settings = @{} } | ConvertTo-Json
$project = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8081/api/v1/projects -Headers $headers -ContentType application/json -Body $body
$project
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8081/api/v1/projects -Headers $headers -ContentType application/json -Body $body
Invoke-RestMethod 'http://127.0.0.1:8081/api/v1/projects?limit=2'
Invoke-RestMethod "http://127.0.0.1:8081/api/v1/projects/$($project.projectId)"
```

У двух POST один projectId. С тем же ключом и другим именем получаем 409 IDEMPOTENCY_CONFLICT. Ключ сохраняется 7 дней; после истечения повтор считается новой операцией. Хеш считается от нормализованного JSON запроса: имя обрезается по краям, отсутствующие settings превращаются в `{}`. Порядок ключей JSON не влияет на повтор. Идемпотентность не является запретом проектов с одинаковым именем: другой ключ создаёт отдельный проект.

Проект, начальные настройки и сохранённый ответ записываются одной транзакцией. Драйвер открывает её через `BEGIN IMMEDIATE`: SQLite допускает одного писателя на файл, поэтому конкурентный запрос ждёт завершения транзакции и затем видит сохранённый ответ. Ожидание ограничено `busy_timeout=5000`. Deferred foreign key разрешает создать проект и его первую settingsVersion в одной транзакции; к Commit обе записи уже обязаны существовать.

Пагинация использует пару `(created_at, id)`, а не OFFSET. При одинаковом времени ID задаёт устойчивый порядок. Cursor — непрозрачный base64url JSON этой пары. Список читается по возрастанию времени; это не фиксированный снимок всех проектов, новые проекты могут появиться на последующих страницах.

## Демонстрация оригинала и задания

Команда подготовки — локальный инструмент Backend 1; будущую публичную загрузку он не заменяет. ID должен принадлежать уже созданному проекту. При локальном запуске CLI использует те же пути по умолчанию, что и сервис:

```powershell
$prepared = go run ./cmd/capture-prepare -project $project.projectId -file testdata/sample_protocol/research/01_configuration.pcap | ConvertFrom-Json
```

При Docker-запуске CLI выполняется внутри `laboratory`, чтобы использовать ту же БД Capture и каталог оригиналов:

```powershell
$prepared = docker compose exec -T laboratory capture-prepare -project $project.projectId -file /fixtures/research/01_configuration.pcap | ConvertFrom-Json
$prepared.capture
$jobId = $prepared.job.jobId
Invoke-RestMethod "http://127.0.0.1:8082/api/v1/jobs/$jobId"
docker compose exec -T laboratory capture-prepare -project $project.projectId -file /fixtures/research/01_configuration.pcap
Invoke-RestMethod -Method Post "http://127.0.0.1:8082/api/v1/jobs/$jobId/cancel"
```

Повтор файла в том же проекте возвращает прежние captureId/jobId и `duplicate: true`. После отмены QUEUED и задание, и capture имеют CANCELLED. Отмена не удаляет оригинал. Повтор уже отменённого импорта также возвращает прежнюю операцию; отдельный интерфейс повторного импорта относится к следующему этапу.

Оригинал сохраняется последовательно: staging → потоковая запись и SHA-256 → File.Sync → атомарная публикация через hard link без перезаписи существующего объекта → локальная транзакция capture + job. Каталог `objects/xx/<sha256>` определяется хешем, имя пользователя не становится путём. В Linux синхронизируется каталог публикации. Ограничение файла — 100 МиБ.

Сегодня проверяется сигнатура PCAP/PCAPNG. Это определение формата, а не доказательство структурной корректности всего файла. Полный reader проверит содержимое при последующей индексации.

Если передача оборвалась, временный файл удаляется. Если процесс аварийно завершился в staging, временный файл может остаться: он не опубликован и не используется как оригинал. Если файл опубликован, но транзакция не завершилась, остаётся невостребованный объект; повтор загрузки безопасно использует его по тому же SHA-256. Автоматического удаления таких объектов пока нет. Если метаданные опубликованы, оригинал уже существует. При старте Capture проверяет размер и SHA-256 всех записанных оригиналов и прекращает запуск при несовпадении/отсутствии файла. Общей транзакции между SQLite и каталогом оригиналов нет.

## Задания и сбои

Состояния: QUEUED → RUNNING → SUCCEEDED/FAILED/CANCELLED. Обработчик выбирается по kind. Один активный worker на файл БД удерживает системную файловую блокировку `<database>.worker.lock`; конкурентный worker не начинает восстановление чужих задач. После аварийного завершения процесса ОС освобождает блокировку. Наличие самого файла не означает, что блокировка занята. Выбор задания и смена QUEUED на RUNNING выполняются в одной транзакции `BEGIN IMMEDIATE`. Это локальная очередь: один активный worker на БД, горизонтальное масштабирование на общий SQLite-файл не предусмотрено.

Этап и прогресс хранятся в jobs. Внутри этапа completed не уменьшается; смена этапа допускает начало счётчика с нуля. total может быть неизвестен. Обработчики обязаны учитывать context и использовать callback прогресса. RUNNING отменяется кооперативно: запрос отмены сохраняется в БД, worker наблюдает его, отменяет context и фиксирует итог. QUEUED отменяется сразу.

На рестарте ранее RUNNING получает FAILED с PROCESS_INTERRUPTED, связанный capture — ERROR, незавершённая assembly — FAILED. При ранее запрошенной отмене итог CANCELLED. QUEUED сохраняется в очереди. Самопроизвольное объявление SUCCEEDED исключено; безопасный повтор после частичной индексации потребует отдельной политики и интерфейса. Незавершённая assembly не становится READY.

Проверки используют настоящие временные SQLite-файлы: транзакционный rollback очереди, конкурентное взятие, прогресс, отмена, отказ второго worker, рестарт и атомарное обновление предметного состояния. У каждого сервиса один SQL connection в пуле; для конкурентных проверок также открываются независимые подключения к одному файлу. Включены foreign_keys, WAL, synchronous=FULL. Полные обработчики индексации/сборки подключаются следующими задачами.

## Контрольный корпус

| Файл | Пакетов | Соединений | Запросов / ответов |
|---|---:|---:|---:|
| research/01_configuration.pcap | 158 | 2, SYN в пакетах 1 и 96 | 14 / 14; по поколениям 9/9 и 5/5 |
| research/02_variations.pcapng | 149 | 1 | 15 / 15 |
| research/03_combined_messages.pcap | 51 | 1 | 8 / 8 |
| additional/04_new_observations.pcapng | 77 | 1 | 8 / 8 |

Кандидат framing: magic `A6 5C`, фиксированный заголовок 8 байт; uint16 big-endian на `[2,4)` задаёт длину тела; полная длина `8 + payloadLength`. Для неполного/неоднозначного направления результат INCONCLUSIVE. Поиск следующего magic и заполнение пропуска нулями не применяются. Поля `[4,6)`, `[6,7)`, `[7,8)` пока интерпретируются как кандидат счётчика, типа и команды; семантику должен подтвердить анализ и журнал.

В первом запросе baseline байты сообщения: `A6 5C 00 00 00 01 00 10`. Пакет 4 даёт первые 3 байта с frameOffset 54, пакет 6 следующие 2, пакет 8 последние 3. Поле длины `[2,4)` пересекает TCP-сегменты: пакет 4 `[56,57)` и пакет 6 `[54,55)`. Это конкретный будущий тест SourceMap. Значение 54 относится к этим пакетам; утилита вычисляет смещение из заголовков, отдельный тест с TCP options ожидает 58.

В combined_messages пакет 10 содержит два ответа, а один запрос разделён между пакетами 4/6/8. Следовательно, граница пакета не является границей прикладного сообщения.

| Диагностика | Проверенное ожидание |
|---|---|
| retransmission | Пакет 11 повторяет серверные байты; логические 279 байт сервера не удваиваются, источников становится больше |
| reordered | Пакет 6 приходит после более позднего диапазона; итоговые байты совпадают с baseline combined |
| missing_segment | В серверном направлении 35 неизвестных байт; INCONCLUSIVE |
| snaplen_truncated | Пакет 10 усечён; 31 неизвестный байт серверного направления; INCONCLUSIVE |
| conflicting_overlap | Конфликт серверного streamOffset 13; нельзя молча выбрать один вариант |
| missing_beginning | SYN отсутствует; начало обоих направлений неизвестно; INCONCLUSIVE |
| checksum_offload | 14 исходящих пакетов дают несовпадение checksum; сам файл не доказывает причину, контекст автора указывает offload |
| bad_checksum | Несовпадение checksum пакета 10; ожидается диагностика и отсутствие безусловного PASS |

CSV содержит 109 строк: 45 исходных действий research/additional и 64 повторённых действий diagnostic-вариантов. Копии действий не восстанавливают потерянные сетевые байты. Набор учебный, Ethernet/IP/TCP и временная шкала сгенерированы; это не проверка полного профиля производительности.
